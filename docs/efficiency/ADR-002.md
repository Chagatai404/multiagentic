# ADR-002: E2 dependency-scoped context and attested plan reuse

Status: accepted implementation scope, 2026-10-26. Base: `1090be9` (E0/E1 checkpoint).

E0/E1 measure packets and bound configured budgets. E2 reduces repeated context and
repeated planning inside dependency plans without weakening any gate. Both reuse
paths are explicit, bound to what they describe, re-validated at use and fall back to
the existing uncached path with an event when a binding no longer holds.

## Decision

1. **Durable summary index.** When a node integrates, the coordinator records a typed
   `DependencyHandoff` on the plan record: node/task ids, node and integrated commits,
   the last engineer/debugger summary (at most 1000 characters), the review verdict,
   at most 50 changed files, the node's declared interface contracts, the verification
   policy fingerprint and a SHA-256 digest over all of these. It is derived from data
   already persisted; it costs no model call. It names files rather than copying them.
2. **Dependency-scoped context (opt-in).** With `context_reuse: true` in a plan, each
   node launch receives the handoffs of its direct dependencies only. At launch the
   coordinator checks the digest, the policy fingerprint, and that the integrated
   commit is in the launch revision. It marks files changed again since integration
   (`--no-renames`, so a rename invalidates both sides) as stale, telling the role to
   read the current content. Failing handoffs are omitted. A `context_manifest` plan
   event records the revision, each reused digest/stale file and each omission.
3. **Interface contracts.** Plan nodes may declare up to 20 `interfaces` (≤500 chars).
   They are rendered as obligations in the node's own packet, carried in its handoff to
   dependents, and bound by its scope digest.
4. **Human plan attestations.** `eng plan attest PLAN NODE…` (or `--all`) is a human
   CLI action that states a node's own spec is its plan. It binds a scope digest
   (objective with ownership text, acceptance, owned paths, context paths, risk
   override, interfaces), a verification-policy digest (checks, protected paths,
   instructions; budgets/repairs excluded because plans resolve them per node) and the
   integration revision at attestation time. At launch the coordinator rechecks the
   plan/node identity, both digests, revision ancestry, and that no path matching the
   node's ownership changed since the attested revision. The engine rechecks scope and
   policy against the actual task and refuses when the task classifies as high risk. A
   valid attestation satisfies only the initial planner step (checkpoint `prepared`),
   recorded as a planner handoff with invocation id `attestation:<id>` and a
   `planning_attested` event; no provider invocation record is created.
5. **Revocation.** `eng plan attest --revoke` withdraws attestations, including from a
   launched task that has not completed planning. Requests validate every node first
   and change nothing on any failure. Consumed attestations stay on the plan for audit.

## Unchanged gates

Attestations never satisfy independent review, deterministic checks, high-risk task
approval, ownership, protected paths, digest matching, unknown-outcome inspection or
manual promotion. High-risk nodes cannot be attested. Planning that becomes due later
(changed-path escalation after implementation) always uses the model planner. The MCP
server exposes no attestation tool; models cannot grant one. Reuse never mutates
specs: plan specs remain immutable after creation.

## Uncached path

With `context_reuse` false (default) and no attestation, packets, role sequences and
invocations are identical to E1; no manifest event is written. The handoff index is
still recorded because it is metadata only. The in-memory content cache stays off.

## Evidence boundary

Offline tests show the attested arm removes one planner CLI invocation per eligible
complex node while engineer, checks and review still run, and that handoffs reach
dependents. They establish orchestration behavior only. Whether shorter planning or
dependency summaries reduce real provider tokens, cost or quality requires the
separately authorized live protocol in [BENCHMARKS.md](BENCHMARKS.md); none was run.
E3 routing, E4 loop optimization and E5 presets remain deferred.
