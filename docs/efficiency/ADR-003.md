# ADR-003: E3 explicit classification routing

Status: accepted implementation scope, 2026-10-26. Base: E2 checkpoint `ab49793`.

E3 lets an operator send cheap work to cheaper models or providers and risky work to
stronger ones, without eng guessing. Routing is configuration, not inference: rules
are written by the operator in project or user YAML, matched deterministically on the
existing classification, and every decision is recorded as an event.

## Decision

- `ProjectConfig.routing` is an ordered list (≤50, unique labels) of rules with a
  `when` match (`task_types`, `complexities`, `risks`, `roles`; empty matches any)
  and a target `model` and/or `provider`. First match wins.
- **Model routes** are evaluated for every role invocation with the task's current
  classification. Changed-path escalation therefore selects the matching stronger
  route for later roles. Precedence: explicit task/node model → first matching model
  route → `role_models` → provider default. Each use logs `model_routed`.
- **Capability validation.** Providers declare `model_selection`. A model route for a
  provider that cannot accept a model (a command provider without `model_flag`) is
  skipped with a `route_skipped` event, never forced into a failing invocation.
- **Provider routes** apply to whole tasks, so they cannot name roles. They are
  evaluated once at creation from the initial classification: `eng run` without
  `--provider` (logs `provider_routed`) and plan nodes without a node or plan
  provider. Plans freeze the result as `PlanNode.effective_provider` at creation and
  validate that every selected provider is registered and can edit files before any
  effect. Resume always uses the saved provider. Hook- and MCP-submitted tasks keep
  their existing explicit/default provider selection.
- Tasks snapshot their config, so a running or resumed task keeps the routes it
  started with. `eng plan preview` shows routed providers, initial role models and
  route labels; run-time capability checks and escalation can still change models.

## Unchanged

Routing never changes classification, workflow roles, repairs, review, approval,
checks, ownership or budgets. Selected identity is the routed name; actual model
identity remains whatever the provider reports, usually unknown. Accounting groups
by selected provider/model, which is how an operator compares routes.

## Evidence boundary

Offline tests cover matching, precedence, escalation re-routing, capability skips,
creation-time provider selection and plan freezing with the fake provider. No route
is shown to save money or keep quality; that needs the owner-authorized live protocol.
